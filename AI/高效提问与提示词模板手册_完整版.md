# 1. 先理解：提示词究竟在解决什么问题

提示词（Prompt）并不是某种神秘咒语。它本质上是你给 AI 的任务说明、背景资料、限制条件和交付要求。它的作用是尽量缩小“你想要的结果”和“AI 理解的结果”之间的差距。

可以把一次高质量提问拆成五个问题：

| 你需要说明什么 | AI 需要弄清楚什么 | 示例 |
|---|---|---|
| 目标 | 最终要完成什么？ | 设计一个 Vue 3 代码比较工具 |
| 背景 | 为什么做、给谁用、在什么环境下用？ | 个人使用，部署到 Vercel |
| 输入 | AI 应该依据哪些材料？ | 现有代码、报错日志、CSV 文件 |
| 约束 | 哪些事情必须做、不能做？ | 保留现有接口，不引入后端 |
| 交付 | 怎样的结果才算完成？ | 完整项目结构、代码、部署步骤和测试方法 |

**关键区别：**

- “帮我做一个代码比较工具”主要表达了目标，但没有说明环境、功能边界和交付标准。
- “使用 Vue 3 + TypeScript + Vite，基于 Monaco Diff Editor，实现左右可编辑、差异高亮、支持粘贴和清空，项目可部署到 Vercel。请给出完整目录结构、全部关键文件、安装和部署命令，以及至少 3 个验证场景。”则已经接近一份可执行的开发任务说明。

第二种提问并不是因为字数更多就一定更好，而是它减少了关键需求上的歧义。

## 1.1 提示词不是越长越好

提示词太短，容易遗漏重要条件；提示词太长，也可能出现重复、矛盾、重点不清的问题。

建议遵循：

1. **重要信息优先。** 目标、环境、硬性约束和交付要求放前面。
2. **只提供相关上下文。** 与任务无关的经历、背景和资料不必全部粘贴。
3. **明确区分事实与猜测。** 哪些是已知条件，哪些只是你的推测，要写清楚。
4. **把关键要求写成可检查的标准。** 不要只说“做好一点”“尽可能完善”。
5. **复杂任务分阶段。** 先确定方案，再实施，再验证，比一句话要求完成所有事情更容易控制质量。

## 1.2 提示词能做什么、不能做什么

提示词可以帮助 AI 明确任务、减少误解、采用指定格式、优先使用指定资料，并对结果进行自检。但它不能保证：

- AI 一定掌握最新信息；涉及近期变化的内容仍需要核查可靠来源。
- AI 一定能访问你的电脑、数据库、邮箱或内部系统；是否能操作取决于当前可用工具和授权。
- AI 一定能一次生成完全正确的代码；仍然需要运行、测试和审查。
- “请务必准确”就能消除幻觉；更有效的做法是要求提供依据、标记不确定性并允许回答“无法确认”。
- 用户提示词可以覆盖系统或平台更高优先级的规则；不同层级指令可能存在优先级关系。

**实用认识：提示词负责把任务说清楚；资料、工具、模型能力和验证过程共同决定结果质量。**

# 2. 黄金五要素：高效提问的基本骨架

原模板的五要素非常实用，适合绝大多数日常任务。下面把每一项进一步展开。

## 2.1 任务目标（Task）——想让 AI 做什么

不要只写主题，要尽量使用明确的动作词。

常见任务动作：

| 动作 | 含义 | 例子 |
|---|---|---|
| 解释 | 说明概念、原理、机制 | 解释 MCP 的工作机制 |
| 比较 | 按同一维度比较多个选项 | 比较椭圆机与跑步机 |
| 研究 | 搜集资料、归纳证据 | 研究某技术的最新发展 |
| 设计 | 提出结构、方案或架构 | 设计一个 CRM 系统骨架 |
| 实现 | 编写代码或执行具体操作 | 实现左右代码差异比较 |
| 排查 | 定位故障、分析原因 | 排查 TypeScript 类型报错 |
| 评估 | 判断优缺点、风险和适用性 | 评估两种部署方案 |
| 提取 | 从文件或材料中抽取信息 | 从合同中提取付款节点 |
| 改写 | 调整表达方式但保留原意 | 将技术说明改写得更易懂 |
| 制定 | 输出可以执行的计划 | 制定 4 天自驾行程 |
| 核查 | 对具体主张查证 | 核查一项新闻说法是否属实 |

尽量避免只写：

- “聊聊这个。”
- “帮我看看。”
- “分析一下。”
- “给个建议。”

可改成：

- “从背景、核心机制、实际应用、优缺点和常见误区五个方面解释。”
- “检查代码中的逻辑错误、类型问题和边界情况，并按严重程度排序。”
- “比较 A、B、C 三种方案，结合成本、实现难度、维护性和风险给出推荐。”

## 2.2 上下文（Context）——为什么做、用在哪里

上下文决定答案应该采用什么深度和角度。

可以补充：

- **使用场景：** 学习、工作、生产环境、个人项目、教学、汇报、论文等。
- **使用对象：** 初学者、开发人员、管理者、客户、评审人员等。
- **当前阶段：** 了解概念、选型、开发中、上线前、故障处理中。
- **已有基础：** 已经了解什么、尝试过什么、哪些内容不需要重复解释。
- **现实条件：** 预算、时间、人员、设备、网络环境、权限、部署环境。
- **目标用途：** 自己学习、保存收藏、交付团队、用于正式决策或生产系统。

示例：

> 我是 Vue 3 开发者，已经熟悉 Composition API 和 TypeScript。当前目标不是学习 Vue 基础，而是设计一个可以直接部署到 Vercel 的小工具。请把重点放在组件结构、依赖选型、差异算法和部署上。

这段上下文能让 AI 避免花大量篇幅讲解你已经熟悉的基础知识。

## 2.3 输入与约束（Input & Constraints）——依据什么、不能做什么

### 输入材料

常见输入包括：

- 原始文本、需求说明、代码片段。
- 错误信息、运行日志、截图。
- Excel、CSV、JSON、PDF、Word 等文件。
- 数据库表结构、API 文档、配置文件。
- 网址、论文、新闻报道、产品说明。
- 你已经尝试过的方案和结果。

输入材料最好说明来源、时间、版本和可信程度。例如：

> 以下内容是 2026 年 10 月 28 日从官方文档复制的配置说明；其中第二段是我自己的推测，并非官方结论。

### 约束条件

约束可分为五类：

| 约束类型 | 需要说清楚的内容 | 例子 |
|---|---|---|
| 技术约束 | 语言、框架、版本、架构 | Vue 3、TypeScript、Vite |
| 环境约束 | 操作系统、部署、网络、硬件 | Windows 11、Vercel、Docker |
| 功能约束 | 必须实现和不需要实现的功能 | 支持粘贴，不需要账号系统 |
| 修改约束 | 允许修改的文件、接口和数据 | 不改变现有 API，不改数据库结构 |
| 资源约束 | 预算、时间、性能和依赖 | 不使用付费服务，尽量减少依赖 |

建议把要求区分为：

- **必须（Must）：** 不满足就不能验收。
- **应该（Should）：** 尽量满足，除非存在明确理由。
- **可选（Could）：** 有余力再做。
- **禁止（Must not）：** 明确不能发生的事情。

示例：

> 必须：左右两个编辑区域、实时差异高亮、支持复制粘贴。应该：支持语言选择和行号。可选：差异统计。禁止：引入后端服务或要求用户注册。

## 2.4 交付规格（Deliverables）——最终要拿到什么

交付规格不仅是“输出 Markdown”或“给我代码”，还需要明确交付物的完整程度。

例如代码任务可以要求：

- 项目目录结构。
- 完整源码，而不是省略关键部分的伪代码。
- 依赖清单和版本要求。
- 安装、运行、构建、部署命令。
- 环境变量说明及示例配置。
- 测试用例和验证步骤。
- 常见错误与排查办法。
- 已知限制和后续改进建议。

研究任务可以要求：

- 结论摘要。
- 背景与定义。
- 证据和来源。
- 多方观点及争议。
- 风险和不确定性。
- 最终判断及适用条件。

不要仅写“详细一点”。应明确需要哪些章节、需要多少例子、是否需要对比表、是否需要引用。

## 2.5 工具偏好（Tools & Sources）——允许 AI 使用什么

这一项非常重要，因为不同任务依赖的资料和工具不同。

可以明确：

- 是否允许联网搜索。
- 是否优先使用官方文档、论文或政府网站。
- 是否只能依据本次上传的文件。
- 是否允许执行代码、计算或生成图表。
- 是否允许访问外部链接。
- 是否允许使用第三方库或外部 API。
- 是否需要给出资料发布日期、访问日期和引用链接。

示例：

> 涉及产品当前价格、版本和部署限制，请联网核查，以官方文档为主；不要把论坛用户的个人经验当作官方事实。对无法核实的内容明确标注。

另一个示例：

> 本次分析只允许使用我上传的 Excel，不要联网补充或自行填补缺失数据。缺失值请单独统计，不要擅自推算。

# 3. 从五要素升级为八项任务说明

五要素适合快速提问。对于开发、研究、决策等复杂任务，可以增加三项：**范围、验收标准、风险与不确定性**，形成八项任务说明。

| 项目 | 要回答的问题 | 示例 |
|---|---|---|
| 1. 任务目标 | 要完成什么？ | 设计并实现一个代码比较工具 |
| 2. 背景上下文 | 为什么做、给谁用？ | 个人使用，部署在 Vercel |
| 3. 输入资料 | 依据什么材料？ | 当前代码、API 文档、日志 |
| 4. 技术/业务约束 | 有哪些边界？ | Vue 3 + TypeScript，不需要后端 |
| 5. 任务范围 | 做到哪里、不做什么？ | 完成核心比较功能，不做用户系统 |
| 6. 交付规格 | 交付哪些内容？ | 完整代码、部署文档、测试用例 |
| 7. 验收标准 | 怎样才算完成？ | 两侧输入后能正确显示新增、删除和修改 |
| 8. 风险与不确定性 | 哪些地方可能有问题？ | 大文件性能、浏览器兼容性需说明 |

## 3.1 范围（Scope）尤其重要

复杂任务最容易发生的问题，是 AI 自行扩大需求。

例如“做一个 CRM”，可能被理解为：

- 只做页面原型；
- 做前端 + Mock 数据；
- 做前后端完整系统；
- 增加登录、权限、消息通知、报表和审计；
- 甚至增加部署和监控。

因此，必须明确本次任务属于哪种范围：

- **概念说明：** 只讲原理，不写实现。
- **方案设计：** 输出架构和技术选型，不生成完整代码。
- **原型：** 页面和交互可展示，数据可以是 Mock。
- **MVP：** 核心业务流程可以实际运行。
- **生产级实现：** 考虑权限、安全、日志、异常、测试、部署和运维。

## 3.2 验收标准（Acceptance Criteria）

验收标准要尽可能客观、可检查。

不够明确：

> 页面要好用，代码要健壮。

更明确：

> 在 Chrome 和 Edge 当前稳定版中，左右文本框均可编辑；输入相同文本时显示无差异；新增、删除和修改行能够分别高亮；清空任一侧后页面不报错；刷新页面后不要求保留输入内容。

对于分析任务，也可以定义验收标准：

> 每个重要结论必须能追溯到至少一个可靠来源；把事实、推断和个人判断分开；无法确认的说法不得写成确定事实。

## 3.3 风险与不确定性

复杂任务最好明确要求 AI 识别：

- 缺少哪些关键输入？
- 哪些结论依赖假设？
- 哪些实现可能受版本变化影响？
- 哪些结果尚未实际运行或验证？
- 哪些风险可能造成数据丢失、费用增加或安全问题？

建议使用：

> 不要为了给出完整答案而虚构缺失信息。请区分已知事实、合理假设和待确认事项，并说明每个关键假设对结论的影响。

# 4. 一份通用提示词模板

下面这份模板可以作为大多数复杂任务的起点。简单问题不必每次填满所有字段。

```text
【任务目标】
我希望你完成：
[清楚说明要解决的问题或要交付的成果]

【背景与用途】
使用场景：[工作/学习/个人项目/生产环境/汇报等]
使用对象：[自己/开发团队/客户/管理者/初学者等]
当前情况：[已经完成什么、遇到什么问题、具备什么基础]

【输入资料】
[粘贴文本、代码、日志、数据，或说明附件/链接]
资料来源及时间：[如适用]
已知事实：[列出确认无误的信息]
我的猜测：[列出尚未确认的判断；没有则写“无”]

【环境与约束】
技术/运行环境：[操作系统、语言、框架、版本、部署环境等]
必须满足：[Must]
尽量满足：[Should]
可以不做：[Could/Out of Scope]
禁止事项：[Must not]

【任务范围】
本次需要做到：[明确范围]
本次不需要做到：[明确排除项]

【工具与资料偏好】
联网：[允许/不允许/只在涉及最新信息时允许]
资料优先级：[官方文档/论文/政府网站/上传文件/指定网站等]
代码执行或数据分析：[允许/不允许/视任务需要]
其他工具限制：[如有]

【交付要求】
输出格式：[Markdown/表格/JSON/代码/文件等]
需要包含：[章节、代码、示例、引用、测试、部署步骤等]
详细程度：[简洁/适中/详细/完整操作手册]
语言与表达：[中文/英文；专业/通俗/面向管理层等]

【验收标准】
满足以下条件才算完成：
1. [标准一]
2. [标准二]
3. [标准三]

【不确定性处理】
如果信息缺失：先指出缺失项；能够合理假设时可以继续，但必须标注假设。
如果无法核实：明确说明，不要编造。
如果存在多个方案：比较主要取舍，并给出推荐及推荐理由。
```

### 使用提醒

- 对简单问题，直接说清楚目标即可，不必填写整份模板。
- 对复杂问题，优先补充环境、边界、交付物和验收标准。
- 已经在对话中说过的信息，不必反复粘贴；可以说“沿用前面确认的环境和约束”。
- 不知道某个字段怎么填，可以留空，并要求 AI 指出真正影响结果的缺失信息。

# 5. 常用任务模板库

以下模板可以直接复制，再替换方括号中的内容。每个模板都尽量包含任务、背景、输入、约束、交付和验收要求。

## 模板 A：联网研究与资料综述

**适用：** 新技术、行业趋势、产品对比、政策法规、人物事件、市场信息、学术主题等。

```text
请围绕【研究主题】进行系统研究，而不是只给出泛泛介绍。

【研究目标】
我希望弄清楚：[具体问题]
重点回答：
1. [问题一]
2. [问题二]
3. [问题三]

【背景与用途】
研究用途：[学习/工作决策/技术选型/投资判断/写作等]
我目前的了解：[已有认知或观点]

【研究范围】
时间范围：[例如 2024—2026 年；或不限]
地域范围：[中国大陆/全球/指定国家或地区]
研究对象：[指定公司、产品、技术、事件或群体]
重点关注：[机制、数据、历史、影响、争议、趋势等]
不需要讨论：[排除项]

【资料与搜索要求】
请联网查证，优先使用：
1. 官方文档、政府/监管机构、原始公告；
2. 论文、研究报告、原始数据；
3. 主流媒体和专业媒体；
4. 社区讨论与用户反馈（仅作为体验或观点证据）。

对重要资料尽量说明发布日期、事件发生日期和来源链接。
如果不同来源口径不同，请解释差异，不要混为一谈。
不要把搜索摘要、未经证实的传言或单一用户体验写成确定事实。

【分析要求】
- 先给核心结论，再给证据和分析过程。
- 区分事实、来源观点、合理推断和个人判断。
- 对重要数据说明统计口径、时间范围和单位。
- 对争议问题呈现主要立场及各自依据。
- 指出证据不足、仍有争议或无法核实的部分。
- 必要时说明资料之间的矛盾和可能原因。

【交付格式】
1. 一页式结论摘要；
2. 背景与核心概念；
3. 关键事实和证据；
4. 分主题详细分析；
5. 不同观点及争议；
6. 风险、局限和不确定性；
7. 最终判断与后续值得关注的问题；
8. 关键来源清单及链接。

请用中文输出，结构清晰、内容具体。引用应紧跟对应事实，不要只在文末堆放链接。
```

### 研究任务的加严选项

- **最新情况：** “重点核查截至【具体日期】仍然有效的信息，区分资料发布日期和事件实际发生日期。”
- **政策法规：** “优先引用现行有效的法律法规、主管机构解释和正式文件，并说明生效日期及适用范围。”
- **学术研究：** “优先检索原始论文和系统综述，说明研究样本、方法、局限及是否存在重复验证。”
- **社区反馈：** “补充 Reddit、专业论坛或用户社区的真实讨论，区分个体体验和总体趋势。”
- **反方检验：** “不要只寻找支持当前判断的资料，也要寻找能够反驳该判断的证据。”

## 模板 B：代码开发与完整项目生成

**适用：** 新项目、功能模块、脚本、前端页面、后端服务、自动化程序等。

```text
请使用【语言/框架/技术栈】实现【具体功能】。

【项目目标】
最终要实现：[用户实际要完成的事情]
主要使用者：[用户群体]
核心使用流程：[用户从哪里开始，经过哪些操作，最后得到什么]

【运行与部署环境】
操作系统：[Windows/Linux/macOS/服务器环境]
语言及版本：[例如 Node.js 版本]
框架及版本：[例如 Vue 3、Vite、TypeScript]
依赖及限制：[指定库、禁止使用的库]
部署位置：[Vercel/Docker/内网服务器/其他]
网络条件：[公网/内网/可能无法访问某些服务]

【功能需求】
必须实现：
1. [功能一]
2. [功能二]
3. [功能三]

应该实现：
1. [体验或性能要求]

本次不做：
1. [明确排除的功能]

【输入与输出】
输入：[数据来源、格式、字段和示例]
输出：[页面、文件、API 响应或数据库变化]
异常输入：[空值、重复数据、超长文本、非法参数等]

【架构与代码约束】
- 使用 [指定架构/组件组织方式]。
- 保留现有 [接口/目录/数据库结构]。
- 不要擅自删除或重命名已有功能。
- 配置和密钥放在环境变量中，不要写死在源码里。
- 对外部输入进行校验，对异常进行合理处理。
- 尽量控制依赖数量，并说明新增依赖的用途。
- 关键逻辑添加必要注释，但不要为每一行代码添加无意义注释。

【交付内容】
1. 技术方案和架构说明；
2. 完整项目目录结构；
3. 每个必要文件的完整代码；
4. package/dependency 配置；
5. 环境变量示例文件；
6. 安装、开发、构建和部署命令；
7. 示例数据或调用示例；
8. 测试代码或可执行验证步骤；
9. 常见错误和排查方式；
10. 已知限制和安全注意事项。

【代码完整性要求】
不要用“此处省略”“其余类似”代替必要代码。
如果内容太长，请按文件分段输出，并明确每个文件的路径。
不要声称代码已经运行成功，除非确实执行并验证过。

【验收标准】
- 按文档步骤可以安装依赖并启动项目；
- 核心功能能够按指定流程运行；
- 至少覆盖正常输入、空输入和异常输入；
- 构建或测试失败时，明确指出错误和修复方式。

请先给出总体实现方案，再给出项目代码和验证步骤。
```

### 开发任务中很值得补充的信息

| 信息 | 为什么重要 | 示例 |
|---|---|---|
| 当前代码结构 | 避免生成与项目不匹配的代码 | `src/components`、`src/views` |
| 已有接口 | 避免随意更改调用契约 | `GET /api/users` |
| 版本信息 | 避免使用不兼容的 API | Vue 3.5、Node.js 22 |
| 部署方式 | 影响构建和环境变量 | Vercel、Docker Compose |
| 权限模型 | 防止越权访问 | 管理员、普通用户 |
| 数据规模 | 影响性能设计 | 约 10 万条记录 |
| 安全要求 | 避免泄露或破坏数据 | 密钥不入库、操作需鉴权 |

## 模板 C：Debug 与故障排查

**适用：** 编译错误、运行异常、接口失败、数据库问题、性能问题、部署失败。

```text
请帮助我定位并解决下面的问题。不要只给可能原因的罗列，请优先根据证据缩小范围。

【问题现象】
预期行为：[原本应该发生什么]
实际行为：[实际发生什么]
发生频率：[每次/偶发/特定条件下]
影响范围：[单个用户/所有用户/某个环境]

【错误信息】
完整错误栈/控制台日志：
[粘贴错误信息]

【相关代码】
[粘贴最小可复现代码，并标注文件路径]

【环境信息】
操作系统：[版本]
语言/框架：[名称及版本]
运行环境：[Node/Python/浏览器/数据库等版本]
部署环境：[本地/测试/生产]

【复现步骤】
1. [步骤一]
2. [步骤二]
3. [出现错误]

【已经尝试过的操作】
- [尝试一]，结果：[结果]
- [尝试二]，结果：[结果]

【修改边界】
允许修改：[文件、函数或模块]
禁止修改：[接口、数据库结构、公共类型或其他模块]
是否允许增加依赖：[是/否]
是否允许重构：[仅必要部分/允许]

【请按以下顺序输出】
1. 最可能的根因，以及支持该判断的证据；
2. 其他可能原因，按概率或排查优先级排序；
3. 最小修复补丁，标注文件路径和修改位置；
4. 修复原理，解释为什么能解决问题；
5. 验证步骤，包括正常路径和边界情况；
6. 可能的副作用、兼容性风险；
7. 回滚方法。

不要在没有证据时把猜测说成确定原因。如果需要更多信息，请指出最有价值的一项日志、代码或检查结果。
```

### Debug 的三个关键技巧

1. **提供完整错误栈，而不只是最后一行。** 调用链和上下文经常决定真正原因。
2. **提供最小可复现案例。** 尽量剔除与问题无关的代码，但保留能稳定触发错误的部分。
3. **要求先定位，再修改。** 不要让 AI 在不清楚原因时大范围重构。

可追加：

> 请先提出 1—3 个最有区分度的检查步骤。每一步说明检查目的、预期结果，以及不同结果分别意味着什么。不要一次提出十几项低价值检查。

## 模板 D：数据分析与图表

**适用：** Excel、CSV、数据库导出、业务指标、实验数据、财务数据等。

```text
请基于我提供的数据完成分析，并给出可复核的结论。

【分析目标】
希望回答：[具体业务/研究问题]
核心指标：[指标名称]
分析对象：[产品/地区/部门/客户/时间段等]

【数据说明】
文件：[附件名称]
字段含义：
- 字段 A：[含义、单位]
- 字段 B：[含义、单位]
- 字段 C：[含义、单位]
数据时间范围：[起止日期]
数据来源：[系统/人工录入/公开资料]

【统计口径】
过滤规则：[排除哪些记录]
去重规则：[按什么字段去重]
缺失值处理：[保留/删除/填补；具体规则]
异常值处理：[识别方法及是否剔除]
分组维度：[日期/地区/类别等]
指标计算方式：[公式或业务定义]

【分析要求】
1. 先检查字段、数据类型、缺失值、重复值和异常值；
2. 明确实际使用的数据行数和过滤过程；
3. 按指定口径计算指标；
4. 分析趋势、差异、相关性或异常现象；
5. 不要把相关性直接解释为因果关系；
6. 如果样本量不足或口径有局限，明确说明。

【图表要求】
图表类型：[折线图/柱状图/散点图/箱线图/饼图等]
横轴：[字段和单位]
纵轴：[指标和单位]
分组/颜色：[类别]
输出格式：[PNG/SVG/PDF]
保存路径：[路径；如适用]

【交付内容】
- 数据质量检查结果；
- 统计口径和计算公式；
- 汇总表；
- 图表及下载文件；
- 3—5 条关键发现；
- 结论、限制和后续分析建议；
- 可复现的代码或公式。

不要擅自补造数据。所有图表必须能追溯到明确的数据和统计口径。
```

### 数据分析特别注意

- “平均值”可能受极端值影响，必要时同时报告中位数和分位数。
- 时间序列需要检查时间粒度、时区、缺失日期和季节性。
- 百分比要说明分母；增长率要说明基期。
- 饼图只适合组成关系清楚、类别数量较少的场景。
- 相关性不等于因果关系，不能仅凭同时变化就断定一方导致另一方。

## 模板 E：改写、润色与翻译

**适用：** 工作邮件、技术文档、报告、学术文字、产品说明、中文英文互译等。

```text
请处理下面这段文字。

【原文】
[粘贴原文]

【任务类型】
[润色/改写/缩写/扩写/翻译/校对/调整语气]

【目标读者】
[普通读者/客户/技术人员/管理层/学术评审/海外用户]

【写作目标】
希望达到：[更清晰/更简洁/更正式/更有说服力/更自然等]

【风格要求】
语气：[正式/自然/专业/友好/客观/坚定]
语言：[简体中文/繁体中文/英文/中英对照]
避免：[套话、夸张、官腔、过度口语化、重复表达等]
术语处理：[保留英文术语/首次出现时中英对照/统一译法]

【内容边界】
- 保留原文核心事实、观点、数据和逻辑；
- 不得擅自增加原文没有的事实、承诺或结论；
- 不确定的术语或歧义请标注，不要擅自猜测；
- [其他必须保留或不能出现的内容]

【交付方式】
版本 A：[例如严格正式版]
版本 B：[例如自然易读版]
另外提供：[修改要点/术语表/中英对照/修改前后对照]

请先给出完整成稿，再简要说明重要修改。不要只给修改建议而不提供改写后的文本。
```

### 改写任务的常见细分

- **只校对：** 只改错别字、语法、标点，不改变句式和观点。
- **轻度润色：** 保留原有结构，只改善表达流畅度。
- **深度改写：** 可以调整段落顺序和论证结构，但不能改变事实和立场。
- **压缩摘要：** 指定目标字数、保留重点和必须保留的数据。
- **翻译：** 指定目标地区、语气、术语表，以及是否偏直译或意译。

## 模板 F：文件阅读、总结与信息提取

**适用：** PDF、Word、Excel、会议纪要、合同、产品文档、技术方案等。

```text
请阅读我上传的【文件名称】，并严格依据文件内容完成以下任务。

【阅读目的】
我希望了解：[具体问题或需要提取的信息]

【处理范围】
文件范围：[全文/指定章节/指定页码/指定工作表]
重点关注：[主题、字段、条款、数据或结论]
不需要：[排除项]

【分析要求】
- 先识别文件结构、章节和重要信息；
- 所有结论必须能够回溯到文件中的位置；
- 尽量标注页码、章节、表名或行号；
- 区分文件明确写明的内容与根据上下文作出的推断；
- 文件没有提到的信息，明确写“文件未说明”；
- 不要用外部常识替代文件原文。

【交付格式】
1. 文件概要；
2. 与问题相关的核心内容；
3. 关键数据/条款/要求提取表；
4. 重要原文位置或引用；
5. 矛盾、缺失和潜在风险；
6. 需要进一步确认的问题。

如果文件内容较长，请先给出结构和重点，再按主题深入分析。
```

### 对不同文件的补充要求

- **合同：** 区分合同原文、风险提示和法律判断；标注条款编号，不要把一般建议当成法律意见。
- **Excel：** 说明工作表、字段、公式、空值和数据范围；不要只看少数样例就代表整个文件。
- **PDF 扫描件：** 表格、图片、印章和扫描页面可能无法完整提取；对看不清的内容明确标注。
- **技术文档：** 保留配置项、版本号、命令和参数，不要在总结时丢掉关键条件。

## 模板 G：方案比较与决策分析

**适用：** 技术选型、采购、软件工具选择、投资之外的一般业务决策、路线选择等。

```text
请帮助我比较以下方案，并给出有依据的推荐。

【决策问题】
我需要决定：[需要选择什么]
候选方案：A=[...], B=[...], C=[...]

【我的目标】
最重要的目标：[成本/速度/稳定性/易用性/长期维护等]
使用周期：[短期/1—3 年/长期]

【现实约束】
预算：[范围]
时间：[期限]
现有资源：[人员、设备、技术、渠道]
不可接受的情况：[风险或限制]

【比较维度】
请至少比较：
1. 功能与效果；
2. 成本（一次性、持续性和隐性成本）；
3. 实施难度和所需资源；
4. 维护成本和可扩展性；
5. 风险、依赖和潜在缺点；
6. 适用场景及不适用场景。

【分析要求】
- 使用相同维度比较所有方案；
- 区分已知数据、估算值和主观判断；
- 说明每个方案最主要的优势和短板；
- 不要为了选出一个“赢家”而掩盖条件差异；
- 如关键参数缺失，列出假设并说明影响。

【交付格式】
1. 结论先行：推荐哪个方案、适用于什么条件；
2. 方案对比表；
3. 逐项分析；
4. 成本和风险；
5. 为什么不选其他方案；
6. 实施建议和退出/切换方案。
```

可追加：

> 请给出“最优方案”和“次优备选方案”，并指出在什么条件变化下，你会改变推荐结论。

这比单纯问“哪个最好”更有价值，因为很多决策并不存在脱离场景的绝对最优解。

## 模板 H：学习新知识与系统讲解

**适用：** 学技术、理解概念、建立知识体系、准备面试或培训。

```text
请系统讲解【主题】，目标是让我真正理解，并能够在实际场景中使用，而不只是记住定义。

【我的基础】
当前水平：[零基础/了解基本概念/有实际开发经验]
已知内容：[已经了解什么]
学习目的：[工作应用/技术选型/面试/系统学习]

【讲解要求】
请按以下顺序展开：
1. 一句话定义；
2. 为什么会出现、解决什么问题；
3. 核心概念及组成部分；
4. 工作原理和完整流程；
5. 与相近概念的区别；
```

# 6. 怎样把模糊要求改写成可执行要求

提问质量很大程度上取决于你能不能把主观形容词转化为可观察的标准。

| 模糊说法 | 更好的表达方式 |
|---|---|
| 详细一点 | 按背景、原理、流程、案例、优缺点、风险和实践建议展开 |
| 快一点 | 将响应时间控制在指定范围；或优先给出最短可行方案 |
| 好用 | 明确用户操作流程、减少步骤、提供错误提示和撤销能力 |
| 性能好 | 指定数据量、并发量、响应时间和目标设备 |
| 安全 | 明确认证、授权、输入校验、密钥管理、日志和威胁范围 |
| 代码完整 | 给出目录结构、所有必要文件、依赖、命令和验证步骤 |
| 兼容性好 | 指定浏览器、操作系统、运行时和最低版本 |
| 帮我看看有没有问题 | 按功能、边界、异常、安全、性能和可维护性逐项检查 |
| 给个建议 | 列出候选方案、比较标准、现实约束和推荐理由 |
| 尽可能准确 | 给出证据来源、口径、假设及不确定性 |
| 不要太复杂 | 指定技术依赖上限、部署方式和维护成本要求 |
| 专业一点 | 指定读者、术语深度、表达风格和引用要求 |

## 6.1 把“详细”拆成深度级别

可以按任务需要选择：

- **L1 概览：** 定义、用途、核心结论。
- **L2 理解：** 背景、原理、组成部分、概念区别。
- **L3 实操：** 完整流程、具体步骤、配置示例、代码示例。
- **L4 工程：** 架构、边界情况、异常处理、安全、性能和维护。
- **L5 深入研究：** 历史演进、技术细节、不同实现、争议、权衡和前沿进展。

示例：

> 请按 L3—L4 深度展开，重点是能照着完成配置和部署，不需要过多介绍行业历史。

## 6.2 把“快”拆成优先级

“快”可能意味着：

- 尽快给出一个能运行的最小版本；
- 优先解决阻塞问题，不追求一次重构；
- 先给结论，再补充依据；
- 选择开发成本最低的实现；
- 优先完成 20% 最关键功能。

应说明自己具体想要哪一种。

## 6.3 把“最好”变成权衡条件

不存在适用于所有场景的绝对最好。请说明权重：

> 最重要的是稳定性和长期维护，其次是开发速度，成本可以略高。不要为了追求极致性能引入过多复杂组件。

或：

> 预算固定，优先选择部署简单、免费额度足够、迁移成本低的方案。

# 7. 工具与资料使用：联网、附件、代码和外部系统

“是否联网”不是唯一的工具选择。不同任务需要不同证据和执行能力。

## 7.1 什么时候应该要求联网

适合联网核查的任务：

- 最新产品价格、套餐、版本和功能；
- 当前法律法规、政策和监管要求；
- 近期新闻、人物职位、公司变化和事件进展；
- 旅行目的地、交通、开放时间和预约信息；
- 软件库、框架和 API 的当前文档；
- 需要引用外部来源的研究或事实核查。

可以不联网的任务：

- 对你已经提供的文本做改写、翻译或摘要；
- 讲解稳定的基础概念；
- 基于已上传数据做限定范围的计算；
- 不依赖外部事实的创作或头脑风暴。

推荐写法：

> 涉及会随时间变化的信息时请联网核查；稳定的基础原理可以直接解释。请标明核查日期，并优先使用官方来源。

## 7.2 什么时候应该以附件为准

当问题依赖你上传的 PDF、Word、Excel、代码或图片时，应明确：

> 本次任务以附件内容为主要依据。请先读取相关章节/工作表/代码文件，不要根据文件名或少量片段猜测全文内容。若附件没有说明某项信息，请明确指出。

如果允许补充外部资料，可以写：

> 先以附件为依据分析，再用官方资料核查附件中涉及的现行版本或政策变化；请分开标注附件原文和外部补充信息。

## 7.3 什么时候应该执行代码或计算

适合要求执行代码的情况：

- 数据量大、计算步骤复杂；
- 需要生成实际图表或文件；
- 需要验证代码能否运行；
- 需要检查文件结构、批量处理文本或比较数据。

建议明确：

- 是否允许执行代码；
- 是否允许安装依赖；
- 能否访问互联网；
- 输出文件格式与保存位置；
- 是否需要保留原文件、不覆盖输入；
- 哪些测试必须实际执行。

特别注意：**写出代码不等于运行过代码，运行过代码也不等于覆盖了所有场景。** 应要求说明实际执行了哪些验证。

## 7.4 什么时候需要外部系统或工具连接

例如访问 GitHub、邮箱、日历、数据库或内部系统。应说明：

- 目标系统和具体对象；
- 只读还是允许写入；
- 允许执行哪些操作；
- 是否需要先预览再确认；
- 哪些操作绝对不能执行；
- 操作失败时如何处理。

涉及删除、发送、付款、发布、修改生产数据等高影响操作，应要求先展示拟执行内容并取得明确确认。

# 8. 如何定义输出格式与验收标准

## 8.1 不同任务适合不同输出格式

| 任务类型 | 推荐格式 |
|---|---|
| 知识讲解 | Markdown 标题、概念表、流程图、案例 |
| 研究综述 | 摘要、分主题章节、证据引用、结论 |
| 方案比较 | 对比表、权衡分析、推荐条件 |
| 代码项目 | 目录树、分文件代码、命令、测试步骤 |
| Debug | 根因、证据、补丁、验证、回滚 |
| 数据分析 | 统计表、图表、计算口径、分析代码 |
| API 设计 | Endpoint 表、JSON Schema、请求响应示例 |
| 文件提取 | 结构化表格、来源位置、缺失项 |
| 决策建议 | 结论、假设、风险、备选方案 |

## 8.2 明确是否需要引用

如果需要引用，不要只说“加引用”，而要说：

- 优先引用什么来源；
- 是否要求原始来源；
- 是否需要发布日期；
- 引用放在正文还是文末；
- 是否需要可点击链接；
- 是否要求每项重要事实都能追溯。

示例：

> 对最新政策和产品功能，请引用官方公告或官方文档；对第三方观点可以引用专业媒体。引用紧跟对应结论，并标明发布日期。无法找到可靠来源的内容不要写成确定事实。

## 8.3 明确代码交付的完整度

“给出代码”有很多种含义：

1. 伪代码：解释思路，不保证运行。
2. 代码片段：展示某一关键逻辑。
3. 最小可运行示例：能够独立运行，但不一定是完整项目。
4. 完整项目：包含必要文件、依赖和配置。
5. 可部署项目：再加部署配置、环境变量、构建与发布说明。
6. 可维护的工程实现：再考虑测试、日志、安全、监控和维护。

请按真实需要指定级别，不要默认每个小问题都需要完整项目。

## 8.4 要求“先结论后依据”时

适合决策、排错和研究任务：

> 请先用 3—5 句话给出结论和推荐，再展开依据、比较和细节。不要为了先给结论而省略必要的不确定性。

# 9. 多轮对话：怎样追问、纠偏和迭代

高质量任务不一定靠一条超长提示词完成。复杂工作通常适合多轮推进。

## 9.1 推荐的四阶段工作法

```text
第 1 阶段：明确问题
    ↓
第 2 阶段：形成方案
    ↓
第 3 阶段：执行与产出
    ↓
第 4 阶段：检查、修正和验收
```

具体做法：

### 阶段一：明确问题

先让 AI 复述它理解的目标、约束和待确认事项。

提示词：

> 先不要开始实现。请整理你理解的需求、已知条件、硬性约束、范围外事项，以及可能影响方案的关键缺失信息。如果有合理默认值，请列出来。

### 阶段二：形成方案

提示词：

> 请给出 2—3 个可行方案，比较成本、复杂度、风险和后续维护，并推荐一个方案。暂时不要生成完整代码。

### 阶段三：执行与产出

提示词：

> 按刚才确认的方案实施。不要擅自改变技术栈和范围；遇到必须调整的地方，先说明原因和影响。每个文件标注路径。

### 阶段四：检查与验收

提示词：

> 请依据最初的需求和验收标准逐项检查。区分已经实际验证、仅通过代码检查推断、尚未验证的项目。列出缺陷、风险和修复建议。

## 9.2 追问时不要只说“继续”

“继续”适合要求接着讲，但如果希望深入某个方面，最好明确方向。

| 简单追问 | 更有效的追问 |
|---|---|
| 继续 | 继续展开 MCP Server 的启动、能力发现和工具调用流程 |
| 详细一点 | 补充实际代码示例、参数结构、返回结果和异常处理 |
| 再讲讲 | 对比它与 Function Calling 的差异，并说明各自适用场景 |
| 优化一下 | 保留当前功能，重点减少依赖、改善错误处理和测试覆盖 |
| 有问题吗 | 按安全、边界情况、性能和兼容性逐项检查 |

## 9.3 发现答案偏离时，直接指出偏差

可以这样纠偏：

> 你刚才的回答偏重概念介绍，但我的重点是实际部署。请保留已经正确的架构说明，把后续内容调整为具体文件、配置、命令和验证流程，不要重新重复前面的基础概念。

或者：

> 你把 A 和 B 当成同一个概念了。请先核对两者定义，再重新比较；如果现有资料无法支持明确结论，请说明。

## 9.4 控制复杂任务的推进节奏

对于大型任务，可以要求分阶段交付，但不要把每一步都变成无意义的确认。

合理方式：

> 先完成需求拆解和总体方案。如果某项信息缺失但不影响主体工作，请采用合理默认值并标注；只有会导致方案明显不同的关键问题才需要向我确认。

# 10. 常见误区与“踩坑词”替换表

## 10.1 含糊表达

| 容易产生歧义的说法 | 建议替换 |
|---|---|
| 好、优秀 | 指定质量维度和验收标准 |
| 快 | 指定优先完成的部分或性能指标 |
| 全面 | 列出必须覆盖的主题和排除项 |
| 详细 | 指定讲解深度和章节结构 |
| 专业 | 指定目标读者和专业程度 |
| 简单 | 指定依赖数量、部署复杂度或操作步骤 |
| 优化 | 指定优化目标：性能、可读性、成本或维护性 |
| 最新 | 指定截止日期，并要求核查来源和发布日期 |
| 完整 | 指定交付物清单和可运行程度 |
| 没问题吧 | 指定检查范围和风险类别 |

## 10.2 常见无效或过度使用的指令

### “你现在是世界顶级专家”

角色设定可能帮助调整表达角度，但不能代替事实、上下文和验收要求。更有效的是写明：

> 请从资深后端工程师的角度审查，重点关注并发、一致性、权限和维护成本。

### “务必保证 100% 正确”

这不是可执行的保证。更好的要求是：

> 对关键结论提供依据；无法核实的部分标注不确定；列出可能影响结论的假设和边界。

### “不要遗漏任何细节”

任务范围没有边界时，“任何细节”无法定义。更好的方式是列出必须覆盖的章节和需要达到的深度。

### “一次性给我全部内容”

复杂任务可能超过单次输出长度或验证能力。更好的方式是明确完整交付目标，并允许按文件或章节分段，确保不省略关键内容。

### “自己发挥”

创意任务可以开放，但涉及代码、数据和正式决策时，至少应明确目标、边界和风险接受程度。

### “展示你所有思考过程”

更有用的要求是让 AI 给出可审查的结论依据，而不是要求冗长的内部思考记录：

> 请提供关键判断依据、使用的假设、计算步骤、证据来源和结论检查过程。

## 10.3 “魔法短语”升级版

这些短语不是魔法，也不能保证结果正确；它们的价值在于让输出更符合你的工作习惯。

| 想达到的效果 | 可以追加的指令 |
|---|---|
| 快速掌握重点 | 先给结论摘要，再展开依据和细节 |
| 控制篇幅 | 先给核心答案，非必要背景不要展开 |
| 深入讲解 | 从定义、原理、流程、案例、边界和实践六个层面说明 |
| 防止编造 | 无法核实的内容请明确标注，不要猜测成事实 |
| 处理信息缺失 | 能合理假设时继续，并单独列出假设及影响 |
| 多方案选择 | 比较主要取舍，给出推荐及推荐成立的条件 |
| 重点优先 | 优先给出 80/20 方案，再列出进阶优化项 |
| 代码可落地 | 给出完整必要文件、安装命令、运行方式和验证步骤 |
| 限制修改范围 | 只修改指定模块；说明每处修改及其影响 |
| 便于保存 | 使用结构化 Markdown，包含目录、表格和可复制代码块 |
| 事实可追溯 | 关键事实附来源，区分原始证据和二手转述 |
| 输出结构化数据 | 严格按指定 JSON Schema 输出，不添加额外文字 |

# 11. 事实、引用、不确定性与隐私安全

## 11.1 区分事实、推断和建议

尤其在新闻、历史、科学、投资、法律和健康等重要领域，建议要求分层表达：

- **事实：** 有可靠资料直接支持的信息。
- **来源观点：** 某个机构、作者或当事方表达的观点。
- **推断：** 根据现有事实推导出来，但并非来源直接确认的判断。
- **建议：** 基于目标、偏好和风险承受能力提出的行动方案。
- **未知：** 目前证据不足或没有可靠资料支持的部分。

可以追加：

> 请不要把推断包装成事实，也不要把某个来源的观点写成已经证实的客观结论。

## 11.2 资料来源要与主张匹配

不同问题需要不同证据：

- 软件功能：优先官方文档、版本发布记录和源代码。
- 法律政策：优先现行法规、正式公告和主管机构解释。
- 学术问题：优先原始研究、系统综述和权威学术资料。
- 历史事件：结合档案、原始文件、当事人材料和严谨研究。
- 用户体验：可以参考论坛讨论，但不能直接推断全体用户。
- 市场价格：需要注明市场、币种、时间和费用口径。

“找到一个链接”不等于“已经核实”。要看来源是否可靠、是否直接支持对应主张，以及资料是否过时。

## 11.3 对不确定信息的处理

可以要求给出：

- 确认程度：高/中/低；
- 依据：支持判断的材料；
- 限制：哪些信息缺失；
- 下一步：需要查什么或测试什么。

不建议强迫 AI 给每个问题都打出看似精确的百分比置信度，因为没有校准依据的数字容易制造虚假的精确感。

## 11.4 保护隐私和敏感信息

提问前检查是否包含：

- 密码、API Key、访问令牌、私钥；
- 身份证件号、银行卡号、账号密码；
- 客户姓名、电话、地址等个人信息；
- 企业内部机密、未公开财务信息；
- 未经授权的源代码、数据或合同内容。

建议先脱敏：

```text
原始：Authorization: Bearer eyJhbGciOi...
脱敏：Authorization: Bearer <REDACTED_TOKEN>

原始：客户张某，电话 138xxxxxxxx
脱敏：客户 A，电话 <REDACTED_PHONE>
```

不要为了让 AI 排错而直接粘贴真实密钥。多数技术问题可以使用脱敏后的变量名和模拟数据复现。

## 11.5 高影响操作应设置确认边界

如果任务涉及删除文件、修改生产数据库、发送邮件、公开发布、购买、付款或其他不可逆操作，建议明确：

> 任何可能产生外部影响或不可逆后果的操作，先给出拟执行内容、对象和影响范围，等待我明确确认后再执行。未经确认只允许分析和准备，不要实际提交。

# 12. 提问前检查清单

复杂任务发送前，可以快速检查以下项目：

### 目标与范围

- [ ] 是否说明最终要解决的问题？
- [ ] 是否说明本次任务做到什么程度？
- [ ] 是否排除了不需要的功能或讨论范围？

### 输入与上下文

- [ ] 是否提供必要背景、环境和版本？
- [ ] 是否提供原始文件、代码、日志或数据？
- [ ] 是否区分已知事实和个人猜测？

### 约束与工具

- [ ] 是否列出必须满足和禁止事项？
- [ ] 是否说明能否联网、执行代码或使用附件？
- [ ] 是否说明资料来源优先级？

### 输出与验收

- [ ] 是否指定输出格式和详细程度？
- [ ] 是否说明必须交付的文件、代码、表格或引用？
- [ ] 是否定义怎样才算完成？
- [ ] 是否要求标注风险、假设和无法确认的事项？

不是每项都必须填写。简单任务通常只需要目标和必要上下文；任务越复杂、风险越高，越值得把边界和验收标准写清楚。

# 13. 极简版：30 秒任务说明模板

适合日常提问，不需要完整填写长模板。

```text
任务：[我希望你完成什么]
背景：[为什么做、用在哪里、我目前的情况]
输入：[提供的材料、数据、代码或链接]
约束：[必须满足、不能做什么]
交付：[格式、深度、必须包含的内容]
工具：[是否联网、是否使用附件、是否执行代码]
验收：[怎样才算完成]

如果信息缺失，请区分关键缺失和非关键缺失。非关键项可以合理假设并标注；关键项只有在会明显改变结果时才向我确认。不要编造无法核实的信息。
```

## 更短的一句话版本

> 请基于【背景和输入】，完成【具体任务】，遵守【关键约束】，交付【格式和内容】，并按【验收标准】检查；不确定的信息请标注，必要时说明假设。

# 14. 附录：不同场景的示范提问

## 示例 1：泛泛提问改成高质量技术问题

**原始问法：**

> 介绍一下 MCP。

**改进问法：**

> 请系统介绍 Model Context Protocol（MCP），面向有一定 Web 开发经验、正在学习 AI Agent 的开发者。先解释 MCP 要解决的问题，再讲 Host、Client、Server 的角色，Tools、Resources、Prompts 的区别，能力发现和调用流程，STDIO 与 Streamable HTTP 的差异。请用一个“AI 助手读取项目文件并调用测试工具”的例子贯穿说明，并比较 MCP 与 Function Calling 的关系。最后给出开发 MCP Server 的入门步骤和常见安全问题。请整理为 Markdown，关键术语提供中英文对照。

## 示例 2：泛泛代码需求改成可交付需求

**原始问法：**

> 帮我用 Vue 写一个代码比较工具。

**改进问法：**

> 使用 Vue 3 + TypeScript + Vite，基于 Monaco Diff Editor 实现一个浏览器端代码比较工具。左右两侧均可编辑，支持粘贴、清空和差异高亮；用户修改任意一侧后，差异能够更新。无需登录和后端，所有处理在浏览器端完成，项目部署到 Vercel。请提供目录结构、完整必要源码、依赖配置、安装和本地运行命令、Vercel 部署步骤，以及相同文本、新增行、删除行、修改行和空输入的验证方法。不要省略关键文件；如果存在 Monaco Editor 的性能或移动端兼容限制，请说明。

## 示例 3：泛泛 Debug 改成可定位的问题

**原始问法：**

> TypeScript 报错，怎么解决？

**改进问法：**

> 在 TypeScript 的 `try...catch` 中，访问 `err.message` 时出现类型错误。当前环境是 [TypeScript 版本]，代码如下：[粘贴最小代码]。请解释 catch 变量的类型规则，给出推荐写法，并比较 `unknown`、类型守卫和自定义错误类型的适用场景。要求兼顾运行时安全，不要简单使用 `any` 绕过类型检查。最后给出可直接复制的代码示例。

## 示例 4：泛泛研究改成事实核查

**原始问法：**

> 网上说某公司造假，是真的吗？

**改进问法：**

> 请核查以下具体说法：[逐条粘贴主张]。先确定事件发生时间和相关主体，再查找监管文件、法院文书、公司公告、原始数据和可靠媒体报道。每条主张分别标注“有证据支持、部分支持、证据不足或与证据冲突”，并说明判断依据。区分事件发生日期和报道发布日期，不要把网络转述当成原始证据。最后整理时间线、主要争议和仍无法确认的细节。

## 示例 5：泛泛分析文件改成可追溯分析

**原始问法：**

> 帮我总结这个 PDF。

**改进问法：**

> 请阅读上传的 PDF，先整理目录和章节结构，再重点总结第 2—4 章。输出每章的核心观点、关键数据、重要定义和作者结论，并标注对应页码。对于文件没有说明的内容，请写明“文件未说明”；不要使用外部资料补齐。最后列出作者论证中仍需核实的假设或证据缺口。

# 最后：记住这五句话

1. **先说目标，再给背景。** 不要让 AI 猜测你真正想解决的问题。
2. **给约束，也给边界。** 说清楚必须做什么、不能做什么，以及本次不做什么。
3. **交付要具体，验收要可检查。** “完整、专业、详细”都应该进一步拆成标准。
4. **重要事实要有来源，重要代码要有验证。** 生成结果不是验证结果。
5. **复杂任务分阶段推进。** 先对齐需求，再设计方案，随后执行，最后检查验收。

> **一条真正好用的提示词，不是把所有要求堆在一起，而是把关键要求讲清楚，让 AI 能够正确理解、有效执行，并让你有办法判断结果到底好不好。**
