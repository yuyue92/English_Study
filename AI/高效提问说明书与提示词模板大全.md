# 第一部分：方法论

## 1. 提问的本质

大模型不会读心。它只能根据你给的文字**推测**你想要什么。提问质量 ≈ 回答质量的上限。

```
模糊的问题  → 模型"猜"你的意图 → 结果泛泛而谈、跑偏、需要反复追问
清晰的问题  → 模型"执行"明确指令 → 结果精准、可直接使用
```

**一个好问题，等于把「脑子里的上下文」搬到屏幕上。** 你知道的背景、偏好、限制，模型一概不知，除非你写出来。

---

## 2. 黄金五要素（详解）

### 要素 1：任务目标（想得到什么）

说清楚**最终产物**是什么，而不是只说主题。

| 产物类型 | 示例 |
|---|---|
| 代码 | 可运行脚本、函数、完整项目骨架 |
| 结论 | 是/否判断、推荐方案、优先级排序 |
| 复盘 | 事故复盘、项目回顾 |
| 清单 | Checklist、待办、步骤 |
| 图表 | 折线图、热力图、流程图 |
| 文本 | 摘要、邮件、论文段落、PPT 大纲 |
| 结构化数据 | JSON、CSV、Markdown 表格 |

✅ 好：「帮我写一个**可直接运行**的 Python 脚本，批量把 CSV 转成 Parquet。」
❌ 差：「讲讲 CSV 和 Parquet。」（产物不明确）

### 要素 2：上下文（背景与用途）

告诉模型**为什么要做**、**给谁用**、**用在哪里**。同一个问题，不同用途答案完全不同。

需要交代的内容：
- **场景**：论文、生产环境、内网系统、教学演示、面试准备、个人学习
- **受众**：评审专家、同事、小白读者、老板
- **你的水平**：入门 / 熟练 / 专家（决定讲解深度）
- **已有进展**：做到哪一步了、尝试过什么
- **目的**：用于决策、发表、上线、学习

✅ 好：「这是给**非技术部门领导**看的汇报，需要避免专业术语。」
❌ 差：「写个汇报。」

### 要素 3：输入与约束

**输入**：模型需要处理的原始材料。
- 数据样例（脱敏后给 3–5 行即可）
- 报错信息、日志、代码片段
- 环境信息：OS、Python/Node/Java 版本、依赖库版本、硬件（GPU/内存）、HPC 集群调度器等

**约束**：划定边界。
- **必须**：必须兼容 Python 3.8；必须使用已有接口
- **禁止**：不要引入新依赖；不要修改原文件；不要联网
- **性能/规模**：时间复杂度 O(n log n)；处理 1000 万行；内存不超过 8GB
- **合规**：数据不能出内网；不得使用 GPL 协议库

> 约束写得越具体，越能避免「看似正确但用不了」的答案。

### 要素 4：交付规格

决定「拿到手能不能直接用」。

| 维度 | 可选项 |
|---|---|
| 格式 | Markdown、JSON、CSV、表格、纯代码块、LaTeX |
| 长度 | ≤300 字、5 条要点、不超过一页 |
| 语言 | 中文 / 英文 / 双语对照 |
| 结构 | 先结论后依据、分步骤、带目录 |
| 引用 | 是否附来源链接、引用数量上限 |
| 语气 | 严谨学术、通俗口语、正式公文 |
| 附加物 | 测试用例、运行命令、风险提示、回滚方案 |

### 要素 5：工具偏好

| 项目 | 说明 |
|---|---|
| 是否联网搜索 | 需要最新信息（新闻、版本、价格、政策）→ 要；纯推理/改写 → 不要 |
| 是否使用上传文件 | 「请**仅基于**我上传的文档回答，不要引入外部信息」 |
| 是否可用外链 | 指定可参考的网址，或限定只用官方文档 |
| 是否执行代码 | 需要精确计算、画图、处理文件时，明确允许运行代码 |

## 3. 魔法短语库

> 任选其一，加在提问结尾即可显著改善输出。

### 3.1 控制结论与结构

| 短语 | 效果 |
|---|---|
| 「**先给结论，后给依据**」 | 避免铺垫过长，直接看答案 |
| 「**用 TL;DR + 详细展开两层结构**」 | 既能速读又能深读 |
| 「**分步骤说明，每步给出验证方法**」 | 便于逐步执行与核对 |
| 「**用表格对比，列出优缺点和适用场景**」 | 方案选择更清晰 |

### 3.2 控制可信度

| 短语 | 效果 |
|---|---|
| 「**必须给出关键引用（≤5 条）**」 | 要求有据可查 |
| 「**区分『已确认事实』与『推测』**」 | 减少幻觉误导 |
| 「**不确定的地方请明确说不确定**」 | 降低编造概率 |
| 「**如果缺失信息，请给出合理假设并标注**」 | 不卡壳，且假设透明 |

### 3.3 控制输出形式

| 短语 | 效果 |
|---|---|
| 「**只输出代码 / JSON，不要解释**」 | 便于程序直接解析 |
| 「**不要客套话，直接输出正文**」 | 去掉「好的，下面是……」 |
| 「**保持原文格式不变，只改动标注部分**」 | 精确局部修改 |

### 3.4 控制决策质量

| 短语 | 效果 |
|---|---|
| 「**若存在多解，给我 80/20 最优解**」 | 用最小成本拿到大部分收益 |
| 「**列出 3 种方案，并给出推荐理由**」 | 有选择余地 |
| 「**先指出我这个问题本身可能存在的误区**」 | 防止在错误前提上深入 |
| 「**最后用一句话告诉我下一步该做什么**」 | 落地行动 |

### 3.5 控制深度

| 短语 | 效果 |
|---|---|
| 「**像给大一新生讲解一样**」 | 通俗 |
| 「**面向该领域资深从业者，省略基础概念**」 | 专业 |
| 「**先自己复核一遍答案再输出**」 | 提升准确率 |

## 4. 提示词的通用结构

推荐使用「分块 + 标题」的结构，清晰且便于模型解析：

```text
# 角色（可选）
你是一名【领域】专家……

# 任务
【要做什么，产物是什么】

# 背景
【为什么做、给谁用、已有进展】

# 输入
【数据 / 代码 / 报错 / 文本，用 ``` 或 """ 包裹】

# 约束
- 必须：……
- 禁止：……
- 规模/性能：……

# 交付格式
- 格式：……
- 长度：……
- 语言：……
- 引用：……

# 工具
- 联网：要 / 不要
- 仅基于上传文件：是 / 否

# 其他
若信息缺失，请自行合理假设并标注。
```

**小技巧**：
- 用 `"""` 或 ` ``` ` 把**数据**与**指令**隔开，避免混淆（也能降低提示词注入风险）。
- 指令放在**开头和结尾各强调一次**，长文本场景尤其有效。
- 一次只提**一个主任务**，多任务请分步或明确编号。

# 第二部分：极简版与填空卡

## 极简版（一行流）

```text
任务【×】；背景【×】；输入【×】；约束【×】；交付【×】；是否联网【要/不要】；若信息缺失请自行假设并标注。
```

## 填空卡（五要素版）

```text
【任务目标】我想得到：__________
【上下文】  用途/场景：__________；受众：__________；我的水平：__________
【输入】    数据/代码/报错：__________
【约束】    必须：__________；禁止：__________
【交付规格】格式：__________；长度：__________；语言：__________；是否带引用：__________
【工具偏好】联网：要/不要；仅基于上传文件：是/否
【收尾短语】先给结论，后给依据；缺失信息请假设并标注。
```

## 超短版（日常快问）

```text
请用【身份/风格】，帮我【做什么】，输出【格式】，不超过【字数】。
```

## 模板 A：联网研究 / 文献综述

**适用**：技术选型调研、行业分析、学术文献综述、竞品调研、政策梳理。

```text
# 任务
请联网检索并撰写一份关于【主题】的【综述 / 调研报告 / 对比分析】。

# 背景
- 用途：【论文引言 / 内部决策 / 技术分享】
- 读者：【评审专家 / 技术负责人 / 初学者】
- 关注重点：【例如：近三年进展、主流方案、争议点、局限性】

# 检索与来源约束
- 时间范围：【2022 年至今】
- 优先来源：【官方文档 / 顶会论文 / 权威机构报告 / 官方博客】
- 排除来源：【营销软文、无出处的自媒体、论坛猜测】
- 引用要求：关键结论必须附来源链接，引用不超过【5】条，不要编造文献

# 交付格式
1. TL;DR（≤150 字，先给结论）
2. 背景与问题定义
3. 主要方案/流派对比（表格：方法 | 原理 | 优点 | 缺点 | 适用场景）
4. 关键争议与未解决问题
5. 趋势判断与建议
6. 参考来源列表（标题 + 链接 + 发布时间）

# 边界
- 区分「已证实事实」「业界共识」「个人推测」，并分别标注
- 若检索不到可靠信息，请明确说明，不要编造
- 语言：【中文】；篇幅：【约 1500 字】
```

**进阶追问**：
- 「请再针对【某方案】做深入，补充实际落地案例与踩坑点」
- 「请检查上述结论中哪些依据较弱，并说明如何验证」

## 模板 B：生成代码（一次可运行）

**适用**：写脚本、工具函数、小型项目骨架。

```text
# 任务
用【语言】实现【具体功能】。

# 环境
- 操作系统：【Ubuntu 22.04 / Windows 11 / macOS】
- 语言/运行时版本：【Python 3.10】
- 依赖库及版本：【pandas==2.1.0, numpy>=1.24】
- 硬件/资源：【16GB 内存、无 GPU / 4 核 CPU】
- 运行方式：【命令行 / 定时任务 / 集群 Slurm】

# 输入输出
- 输入：【文件路径 / 格式 / 样例（给 3 行）】
- 输出：【输出文件格式及保存路径 / 日志路径】
- 示例：
  输入：【……】
  期望输出：【……】

# 约束
- 不要改动原有文件与接口：【文件 / 函数签名】
- 性能目标：【处理 100 万行 ≤ 30 秒】；复杂度不高于【O(n log n)】
- 代码风格：【PEP8 / 类型注解 / 中文注释】
- 禁止：【引入新的第三方依赖 / 使用已废弃 API】

# 交付要求
请给出**完整可运行**的内容：
1. 项目目录结构
2. 依赖安装命令（含 requirements.txt）
3. 完整源码（无省略号、无「此处略」）
4. 命令行运行示例
5. 至少【3】个测试用例（含边界情况：空输入、异常输入）
6. 关键设计说明（≤5 行）

# 输出方式
先给代码，再简要解释；如有不确定处，请合理假设并标注。
```

**提示**：
- 对大型任务可要求「**先给设计方案和文件列表，我确认后再逐文件生成**」。
- 要求「**不要使用省略号，请输出完整文件**」可避免模型偷懒。

## 模板 C：Debug（精确定位）

**适用**：报错排查、行为异常、性能问题。

```text
# 任务
请定位并修复下面的问题：【一句话描述现象，例如：运行时报 KeyError / 结果与预期不符 / 接口偶发超时】

# 问题现场
- 期望行为：【……】
- 实际行为：【……】
- 复现步骤：
  1. 【……】
  2. 【……】
- 报错栈 / 日志（完整粘贴，勿截断）：
```
【粘贴错误栈或日志】
```
- 相关代码：
```【语言】
【粘贴最小可复现代码，标明文件名与行号】
```

# 环境
- OS / 版本 / 依赖库版本：【……】
- 部署方式：【本地 / Docker / K8s / HPC】
- 最近变更：【升级了什么、改了什么配置】

# 我已尝试（请勿重复建议）
1. 【尝试 A】→ 结果：【无效，现象……】
2. 【尝试 B】→ 结果：【……】

# 约束
- 只允许修改：【文件 / 函数名】
- 不得修改：【对外接口、数据库表结构、公共库】
- 需兼容：【版本 / 平台】

# 交付
按以下顺序输出：
1. **最小补丁**（diff 格式或修改后的完整函数）
2. **根因分析**（为什么会出现，按可能性排序，标明置信度）
3. **验证步骤**（如何确认已修复，含测试命令）
4. **风险与回滚**（补丁可能的副作用、如何回滚）
5. **预防建议**（如何避免再次发生，≤3 条）

先给补丁再解释。信息不足时，请告诉我还需要提供哪些日志/信息，而不是盲目猜测。
```

**Debug 提问的三大铁律**：
1. **完整贴错误栈**，不要只说「报错了」。
2. **给最小可复现代码**，而不是整个项目。
3. **说明已尝试过的方法**，避免重复无效建议。

```

```

**提示**：如果模型支持执行代码，补一句「**请实际运行代码并给出真实结果，不要凭空编造数字**」。

# 第四部分：进阶技巧

## 1. Few-shot（给示例）

比起写一大段规则，**给 2–3 个输入→输出示例**往往更有效。示例要覆盖典型情况与一个边界情况。

```text
按下面的风格改写标题：
输入：公司召开年度会议  →  输出：年度大会落幕，三大战略浮出水面
输入：新产品发布      →  输出：【请你来写】
```

## 2. 分步思考（Chain of Thought）

复杂推理任务可加：
- 「请**逐步推理**，每一步写出依据，最后再给结论」
- 「先列出解题思路，再执行计算」

> 部分新一代推理模型会自行深度思考，此时不必刻意要求逐步输出，重点把**目标与约束**写清楚。

## 3. 让模型先提问（反向澄清）

信息不足时特别有用：

```text
在开始之前，请先向我提出不超过 5 个最关键的澄清问题；
我回答后你再正式输出。
```

## 4. 自检与二次校验

- 「输出前请先对照约束清单自查一遍，不符合的先修正」
- 「请列出你这份答案中**最可能出错的 3 个地方**，并说明如何验证」
- 「请扮演严格的评审，挑出上述方案的漏洞」

## 5. 角色 + 视角切换

- 「请分别以**架构师、测试工程师、运维**三种视角评估这个方案」
- 「请先给出支持方观点，再给出反对方观点，最后给出你的综合判断」

## 6. 任务拆解（长任务分阶段）

```text
阶段 1：只输出大纲，等我确认
阶段 2：逐章节展开，每次一章
阶段 3：全文统稿，统一术语与风格
```

## 7. 分隔符与结构化输入

- 用 `"""`、``` 、`<doc></doc>` 等包裹长文本与代码
- 多份材料用编号：`【材料1】【材料2】`，并在指令中引用编号

## 8. 约束的「正反」双写

- 正向：必须做什么
- 反向：绝对不要做什么
- 优先级：「若规则冲突，以【安全 > 准确性 > 格式 > 文采】为序」

## 9. 要求「可验证」的输出

- 代码：附测试用例与运行命令
- 结论：附数据来源与计算过程
- 建议：附判断条件与失败时的退路

## 10. 控制模型「偷懒」

- 「请输出**完整内容**，不要使用『此处省略』『其余同理』」
- 「共有 N 项，请逐项列出，最后核对数量」

# 第五部分：踩坑词与替代说法

## 5.1 含糊词 → 可度量指标

| ❌ 含糊说法 | ✅ 更好说法 |
|---|---|
| 写得**好**一点 | 逻辑更清晰、句子不超过 25 字、每段只有一个中心句 |
| 跑得**快**一点 | 处理 100 万行从 60s 降到 10s 以内 |
| **优化**一下 | 在不改变接口的前提下，将内存占用降低 50% |
| **详细**说明 | 每个步骤包含：目的、命令、预期输出、常见错误 |
| 简单点 | 不超过 300 字，不用专业术语，配 1 个类比 |
| 专业点 | 采用学术写作规范，术语准确，被动语态，引用格式 GB/T 7714 |
| 适当 | 控制在 3–5 条 |
| 一些例子 | 给出 3 个例子，覆盖正常、边界、异常情况 |

## 5.2 偏弱请求 → 可交付请求

| ❌ 偏弱请求 | ✅ 替代说法 |
|---|---|
| 给我**一段代码** | 给我**完整可运行脚本** + 测试用例 + 运行命令 |
| 帮我**看看有没有问题** | 请列出**几条可验证的检查项**，逐项给出通过/不通过及依据 |
| 帮我**写个方案** | 请写一份方案，含目标、范围、里程碑、风险、资源，≤2 页 |
| **总结**一下 | 用 5 条要点总结，每条 ≤30 字，并列出 3 个关键数据 |
| 帮我**翻译** | 翻译为【目标语言】，面向【读者】，术语保持【术语表】，保留格式 |
| 帮我**分析**数据 | 分析【指标】随【维度】的变化，给出趋势、异常点、3 条结论 |
| **解释**一下 | 用类比讲清本质，再给最小示例，最后指出 3 个常见误区 |
| 这个**对不对** | 请逐条核对事实与逻辑，标注「正确 / 存疑 / 错误」及依据 |

## 5.3 容易引发幻觉的提问方式

| 风险提问 | 改进 |
|---|---|
| 「请给我 10 篇相关文献」 | 「请联网检索，只列出你能确认真实存在的文献并附链接；不确定的请标注」 |
| 「某某人说过什么名言」 | 「请给出可验证的出处，不确定就明说」 |
| 「帮我编一些数据」 | 「请给出**明确标注为模拟**的示例数据」 |
| 「最新版本是什么」 | 「请联网确认，并写明查询日期与来源」 |

# 第六部分：多轮对话与迭代策略

## 6.1 迭代的黄金流程

```
1. 先要「骨架」  →  大纲 / 方案 / 文件列表
2. 确认方向      →  修正偏差，成本最低
3. 再要「血肉」  →  逐部分展开
4. 精修         →  针对局部提出具体修改意见
5. 终检         →  让模型按清单自查
```

## 6.2 高效的追问句式

| 目的 | 追问模板 |
|---|---|
| 局部修改 | 「只改第 3 段，其他保持不变，要求：……」 |
| 加深 | 「针对第 2 点，补充原理、案例和常见坑」 |
| 缩短 | 「压缩到 50%，保留数据与结论」 |
| 换风格 | 「同样内容，改成面向【读者】的口吻」 |
| 质疑 | 「你的依据是什么？有没有反例？」 |
| 复核 | 「请重新检查计算过程，逐步写出」 |
| 换方案 | 「如果不能使用【某技术】，还有什么替代方案？」 |

## 6.3 何时该「新开对话」

- 话题已完全切换
- 对话很长，模型开始遗忘早期约束或出现前后矛盾
- 前面出现过错误引导，想「清零」重来

> 新开对话时，把**关键背景与最终约束**压缩成一段「上下文摘要」带过去。

## 6.4 长对话保持一致性

- 开头设定「**全局规则**」：「以下规则在整个对话中始终有效：……」
- 每隔若干轮让模型「**复述当前约束与进度**」，核对是否一致
- 重要结论让模型整理成「**当前定稿清单**」，后续在此基础上迭代

# 第七部分：提问前自检清单

在按下发送键前，快速过一遍：

- [ ] **产物明确**：我知道自己最终要拿到什么吗？（代码 / 结论 / 清单 / 图表）
- [ ] **背景充分**：用途、受众、我的水平交代了吗？
- [ ] **输入完整**：数据样例、报错栈、代码、环境版本都给了吗？
- [ ] **约束清晰**：必须做什么、禁止做什么、规模与性能要求写了吗？
- [ ] **格式指定**：格式、长度、语言、是否带引用说清了吗？
- [ ] **工具说明**：是否联网？是否仅基于上传文件？
- [ ] **无含糊词**：「好 / 快 / 优 / 详细」都换成可度量的指标了吗？
- [ ] **单一任务**：一次只问一件事，或已明确编号分步？
- [ ] **可验证**：要求附测试 / 依据 / 验证步骤了吗？
- [ ] **兜底说明**：加了「信息缺失请假设并标注」吗？
- [ ] **隐私安全**：已脱敏（密钥、密码、个人信息、内部机密）吗？

# 第八部分：常见问题（FAQ）

**Q1：提示词是不是越长越好？**
不是。**信息密度**比长度重要。把关键信息写全、无关内容删掉；冗长而混乱的提示词反而干扰模型。

**Q2：我该不该用「你是一名××专家」这类角色设定？**
有帮助但不是万能。角色设定适合调整**语气、视角、专业深度**；真正决定质量的是**任务、约束和交付规格**。角色 + 具体要求 > 只有角色。

**Q3：为什么同样的问题，每次回答不一样？**
模型生成有随机性。需要稳定输出时：约束格式、给示例、降低「创造性」参数（API 中的 temperature），并要求固定结构。

**Q4：模型回答错了，我怎么高效纠正？**
指出**具体错误位置 + 正确信息 + 期望的修改方式**，例如：「第 3 步中 X 的结论有误，正确应为 Y，请据此修正后续推导。」避免只说「不对，重做」。

**Q5：如何减少「一本正经胡说八道」？**
- 要求给出处并**自己核验**
- 限定「仅基于提供的材料回答」
- 允许它说「不知道 / 不确定」
- 要求区分事实与推测
- 对关键结论交叉验证（换提问方式或换模型）

**Q6：贴代码/数据时要注意什么？**
- 先脱敏：去掉密钥、Token、密码、个人隐私、内部地址
- 给**最小可复现**片段，而不是整个仓库
- 标明文件名、行号、版本

**Q7：一个复杂任务该怎么拆？**
按「**先方案、后实现、再验证**」拆；每一步让模型输出**可检查的中间产物**，确认后再进入下一步。

**Q8：System Prompt 和我平时的提问有什么区别？**
System Prompt 是长期生效的「规则与人设」（多用于开发自己的应用）；日常聊天中的提问是 User Prompt，是单次任务需求。在普通聊天里，你可以把「长期规则」放在对话开头或各平台的「自定义指令」中。
